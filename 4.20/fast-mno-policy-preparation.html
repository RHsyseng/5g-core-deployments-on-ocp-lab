Fast MNO Upgrade — Policy Preparation

Introduction

In this section you will perform a fully automated EUS-to-EUS upgrade of the mno managed cluster from 4.18 to 4.20. The cluster has 3 worker MachineConfigPools (worker-0, worker-1, worker-2), each containing 3 nodes in its own Kubernetes failure domain.

Following the ZTP GitOps methodology used throughout this lab, the ACM upgrade policies are defined as PolicyGenerator CRs that reference individual Kubernetes resource files (reference CRs). These files are committed to the ZTP Git repository and ArgoCD automatically deploys the resulting RHACM policies to the Hub cluster. The ClusterGroupUpgrade (CGU) resources that orchestrate the upgrade stages are the only objects applied directly to the Hub cluster.

You will:

  1. Verify that the cluster and Hub components are in the correct starting state.

  2. Create the reference CRs and PolicyGenerator files for the 4.18 → 4.19 upgrade, commit them to the ZTP repository, and confirm ArgoCD deploys them.

  3. Create the reference CRs and PolicyGenerator files for the 4.19 → 4.20 upgrade and worker zone policies in the same way.

  4. Define and apply a chain of ClusterGroupUpgrade (CGU) resources to orchestrate the full upgrade sequence.

  5. Trigger the upgrade and monitor it as it progresses through each stage automatically.

Before starting, make sure you have read and understood the Fast MNO Upgrades — Theory section. All policies and CGUs in this lab are a direct application of the three-pillar methodology described there.

Setting Up the Reference CRs Directory

In the ZTP GitOps workflow, ACM policies are not written by hand as raw Policy YAMLs. Instead, we use a pre-built container image that contains small, focused reference CR files that describe the desired Kubernetes objects, and then declare a PolicyGenerator CR that wraps them into ACM Policies automatically. ArgoCD watches the ZTP Git repository and pushes any new or updated policies to the Hub cluster. Refer to the RHACM Governance Policy Framework and PolicyGenerator Deep Dive sections for background.

The reference CRs are stored in the source-crs/ directory inside the site-policies/fleet/active/v4.19/ and site-policies/fleet/active/v4.20/ directories. 
podman login infra.5g-deployment.lab:8443 -u admin -p r3dh4t1! --tls-verify=false
mkdir -p ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/v4.19/source-crs/reference-crs/
TEMP_ID=$(podman create infra.5g-deployment.lab:8443/openshift4/openshift-telco-core-rds-rhel9:v4.19.4-4)
podman cp $TEMP_ID:/usr/share/telco-core-rds/configuration/reference-crs/. ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/v4.19/source-crs/reference-crs/
podman rm $TEMP_ID
podman login infra.5g-deployment.lab:8443 -u admin -p r3dh4t1! --tls-verify=false
mkdir -p ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/v4.20/source-crs/reference-crs/
TEMP_ID=$(podman create infra.5g-deployment.lab:8443/openshift4/openshift-telco-core-rds-rhel9:v4.20.2-3)
podman cp $TEMP_ID:/usr/share/telco-core-rds/configuration/reference-crs/. ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/v4.20/source-crs/reference-crs/

Custom Manifest for MCP workers

Let’s first create the custom manifest for our MCP worker-0, which does not exist in the reference CRs. It will be created based on the reference CRs for worker-1, worker-2, and worker-3.

You will need to create the custom manifest for your MachineConfigPools workers based on the name you’ve given to your workers. In this case, we’ve named our MCP orkers: worker-0, worker-1, and worker-2. Notice that worker-1 and worker-2 are included as references in the source-crs/reference-crs/custom-manifests/mcp-worker-1.yaml and source-crs/reference-crs/custom-manifests/mcp-worker-2.yaml files, so we can just use them as templates. 
cat <<EOF > ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/v4.19/source-crs/reference-crs/custom-manifests/mcp-worker-0.yaml
---
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-0
  labels:
    machineconfiguration.openshift.io/role: worker-0
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values: [ worker, worker-0 ]
  paused: false
  maxUnavailable: "100%"
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-0: ""
EOF
cat <<EOF > ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/v4.20/source-crs/reference-crs/custom-manifests/mcp-worker-0.yaml
---
apiVersion: machineconfiguration.openshift.io/v1

Automation with ACM and TALM

The entire end-to-end procedure is orchestrated using Red Hat Advanced Cluster Management (ACM) and the Topology Aware Lifecycle Manager (TALM) operator.

  • Policies: ACM Policies are created on the Hub cluster for each distinct upgrade action (e.g., core-upgrade-ocp-19, core-upgrade-olm-19, core-upgrade-ocp-20, core-upgrade-workers-0, etc.). These policies are initially set to remediationAction: inform.

  • Orchestration: A series of ClusterGroupUpgrade (CGU) custom resources are used to trigger and manage these policies in the correct sequence. TALM is responsible for moving policies from an 'inform' state to an 'enforce' state.

  • Sequencing: The blockingCRs stanza within a CGU is used to create dependencies, ensuring that one stage (e.g., the upgrade to 4.20) does not begin until the prerequisite stage (e.g., the upgrade to 4.19) has successfully completed.

This approach transforms a complex, high-risk manual upgrade into a predictable, repeatable, and fully automated zero-touch operation that executes significantly faster than traditional methods.

Creating the 4.18 → 4.19 Upgrade Policies

The core of the automation is a set of ACM Policies that declaratively define the desired state for each step of the upgrade. These policies are applied to the Hub cluster and remain in an inform state until activated by a ClusterGroupUpgrade (CGU).

The following policies are created to manage the upgrade from version v4.18 to v4.19.

In this section we are going to present parts of the PolicyGenerator file that will be used to start the Fast MNO Upgrade. At the end of this section you will create the complete PolicyGenerator file based on the reference core-upgrade PolicyGenerator available in the telco-reference repository here.

Policy: core-upgrade-prep-19

This is the preparation policy. It readies the spoke cluster for the control plane upgrade by:

  • Updating the CatalogSource: It points the redhat-operators-disconnected catalog to the v4.19 index image. This ensures OLM can find the correct operator versions compatible with 4.19.

  • Pausing and Configuring Worker MCPs: It patches all worker MachineConfigPools (worker-0 through worker-3) to set paused: true. This is a critical safety measure to prevent worker nodes from upgrading while the control plane is in motion. It also pro-actively sets maxUnavailable: "100%" in preparation for the parallel worker upgrade phase later.

policies:
  - name: core-upgrade-prep-19
    policyAnnotations:
      ran.openshift.io/soak-seconds: "30"
    manifests:
      - path: v4.19/source-crs/reference-crs/required/other/catalog-source.yaml
        patches:
        - spec:
            image: infra.5g-deployment.lab:8443/redhat/redhat-operator-index:v4.19-1772552013
        - status:
            connectionState:
              lastObservedState: READY
      # Provide the required acknowledgement of the upgrade. This
      # assumes that the verification has been done during planning
      # lab/certification phase of project
      # - path: reference-crs/optional/other/upgrade-ack.yaml
      #   patches:
      #   - data:
      #       ack-4.15-kube-1.29-api-removals-in-4.16: "true"
      - path: v4.19/source-crs/reference-crs/custom-manifests/mcp-worker-0.yaml
        patches:
        - spec:
          # Adjust as needed based on spare capacity, cluster design, and application requirements
            maxUnavailable: "100%"
            paused: true
      - path: v4.19/source-crs/reference-crs/custom-manifests/mcp-worker-1.yaml
        patches:
        - spec:
          # Adjust as needed based on spare capacity, cluster design, and application requirements
            maxUnavailable: "100%"
            paused: true
      - path: v4.19/source-crs/reference-crs/custom-manifests/mcp-worker-2.yaml
        patches:
        - spec:
          # Adjust as needed based on spare capacity, cluster design, and application requirements
            maxUnavailable: "100%"
            paused: true

Policy: core-upgrade-ocp-19

This is the main upgrade policy. Its sole purpose is to target the ClusterVersion resource on the spoke cluster and instruct it to begin the upgrade. It sets the desired channel to stable-4.19 and provides the specific image and version (4.19.24) for the cluster to upgrade to.

To obtain the correct image digest for your mirror registry, run:

podman login infra.5g-deployment.lab:8443 -u admin -p r3dh4t1! --tls-verify=false --authfile ~/.docker/config.json
oc adm release info --registry-config ~/.docker/config.json 4.19.24 | grep 'Pull From: '

Replace the image value below with the output of that command.

policies:
  - name: core-upgrade-ocp-19
    manifests:
      - path: v4.19/source-crs/reference-crs/optional/other/ClusterVersion.yaml
        patches:
        - spec:
            channel: stable-4.19
            desiredUpdate:
              # Replace version, image and status below with desired version
              version: 4.19.24
              image: infra.5g-deployment.lab:8443/openshift/release-images@sha256:3ef832b8bb0d56331035ba54af36c36be46d6c6dc1a41e300055692f02bb001d
              force: true
        - status:
            history:
            - version: 4.19.24
              state: "Completed"

The PolicyGenerator for 4.18 → 4.19

Now create the PolicyGenerator CR that bundles the reference CRs created above into four ACM Policies. The placement.labelSelector block defines which managed clusters receive the policies — TALM will add and remove these labels automatically as the upgrade progresses.

cat <<EOF > ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/core-upgrade-19.yaml
apiVersion: policy.open-cluster-management.io/v1
kind: PolicyGenerator
metadata:
  name: core-upgrade-19
placementBindingDefaults:
  name: core-upgrade-19-placement-binding
policyDefaults:
  namespace: ztp-policies
  placement:
    labelSelector:
      matchExpressions:
        - key: common
          operator: In
          values:
            - ocp418
            - ocp419
        - key: rds
          operator: In
          values:
            - core
        - key: upgrade-fast-418-420
          operator: Exists
  remediationAction: inform
  severity: low
policies:
  - name: core-upgrade-prep-19
    policyAnnotations:
      ran.openshift.io/soak-seconds: "30"
    manifests:

Defining the Worker Upgrade Policies

With the control plane policies ready to be upgraded to 4.20, the worker nodes are still paused. This final stage orchestrates the sequential, parallel upgrade of each worker MachineConfigPool (MCP).

Next, we create a separate policy for each worker MCP. The sole purpose of each policy is to unpause its corresponding MCP by setting paused: false. The MCO on the spoke cluster will see this change and—because we set maxUnavailable: "100%" in the preparation policy—will begin upgrading all nodes in that MCP simultaneously.

Here is the policy for worker-0. This manifest is duplicated for worker-1, worker-2, and worker-3.

Creating the PolicyGenerator for Worker Zone Upgrade

This PolicyGenerator generates one policy per worker MCP zone. Each policy unpauses its zone and waits for all 3 nodes to apply the pending MachineConfig and reboot. The three policies run concurrently, which is what makes this upgrade fast.

The section of the PolicyGenerator for upgrading the workers should look like this:

cat <<EOF > ~/5g-deployment-lab/ztp-repository/site-policies/fleet/active/core-upgrade-finish.yaml

            - ocp419

          operator: In
          values:
            - core

          operator: Exists

Placement and Binding

The PlacementRule and PlacementBinding are included into the PolicyGenerator CRs to apply all the policies related to the upgrade to 4.20, e.g cdocumentation/modules/ROOT/pages/installing-agentbasedinstall-cluster.adocontrol-plane and worker policies.

The placementRule is configured to select all clusters with the following labels: common set to ocp418, ocp419, rds set to core, and the existence of the upgrade-fast-418-420 label. Cluster labeling will be automatically handled by the CGUs generated in subsequent sections.

Upon applying the CGUs custom resources to our MNO cluster, certain labels will be automatically added, while some of the 4.18 and 4.19 upgrade labels will be removed or replaced. This will result in a seamless, automatic upgrade from EUS 4.18 to EUS 4.20.
